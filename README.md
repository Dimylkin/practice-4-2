## 📌 Врезка: что такое API-ресурс и зачем он нужен

**API** — набор адресов сервера, к которому браузер умеет обращаться.
**Endpoint** — один конкретный адрес, например `https://abc123.mockapi.io/books`.
**Схема ресурса** — описание полей, которые сервер хранит и возвращает в ответах. Это контракт JSON, с которым вы будете работать всю практику.

Сервисы [mockapi.io](https://mockapi.io) и [lightboxapi.ru](https://lightboxapi.ru) позволяют поднять свой маленький сервер без написания бэкенда: вы задаёте схему ресурса, а сервис сам принимает GET, POST и DELETE запросы и хранит данные.

> 🔬 **Обязательный эксперимент до написания кода.**
> Откройте URL своего ресурса в обычной вкладке браузера. Вы увидите голый JSON — ровно то, что получит ваш `fetch`. Добавьте одну книгу через интерфейс сервиса и обновите вкладку: JSON изменился. Сервер действительно хранит данные, и теперь вы видели его ответ своими глазами. Запишите в конспект JSON пустой базы и базы с одной книгой — он понадобится в Задании 1.

## 📝 Задание 1. Превращаем mock-api.ts в настоящий сетевой слой (30 мин)

### Шаг 1. Переименуйте файл `src/mock-api.ts` в `src/api.ts`

**Зачем:** имя файла должно отражать суть. Раньше файл *имитировал* сеть (mock — «макет»), теперь он будет отвечать за *настоящие* запросы к серверу. Префикс «mock» стал враньём.

**Как:** в VS Code правый клик по файлу → Rename. Импорт в `main.ts` сразу подчеркнётся красным — это нормально и ожидаемо: мы починим его в Задании 3, а пока не трогаем.

### Шаг 2. Замените константу `STORAGE_KEY` на `API_URL` со своей ссылкой

**Зачем:** раньше «сервером» был `localStorage`, и адресом данных служил ключ `'catalog'`. Теперь источник данных — HTTP-сервер, и его адрес — URL вашего ресурса. Меняется не имя константы, а само понятие «где живут данные».

**Как:** удалите строку `const STORAGE_KEY = 'catalog';` и добавьте:

```typescript
// Адрес вашего личного ресурса на сервере
const API_URL = 'https://ВАША-ССЫЛКА/books';
```

### Шаг 3. Удалите имитацию задержек и сбоев

**Зачем:** функции `delay()` и константы `FETCH_FAIL_RATE` / `SAVE_FAIL_RATE` существовали, чтобы изображать сеть: паузы и случайные ошибки. У настоящей сети задержки и сбои свои, естественные — сервер может отвечать медленно, вернуть 404 или упасть с 500. Искусственная имитация больше не нужна и только мешала бы видеть реальное поведение.

**Как:** удалите функцию `delay` и обе константы вероятностей, а также все вызовы `await delay(...)` и проверки `Math.random() < ...` из тел функций ниже.

### Шаг 4. Добавьте интерфейс ответа сервера (DTO)

**Зачем:** DTO (Data Transfer Object, «объект для передачи») — это формат данных «по проводу», то есть ровно тот JSON, который возвращает сервер. Сервер ничего не знает про ваш интерфейс `Book` из `task1-types.ts`: он отдаёт поля из схемы ресурса, которую вы сами создали. DTO фиксирует этот внешний формат отдельно от внутренней модели. Разделение нужно, чтобы причуды серверного формата не расползались по приложению: о них будет знать только один слой — `api.ts`.

**Как:** добавьте интерфейс и заполните его **из собственного наблюдения** (эксперимент из врезки: вы открывали ссылку во вкладке браузера):

```typescript
// DTO — «транспортный» формат данных: что реально отдаёт сервер
// TODO 0: выпишите поля, которые вы видели своими глазами во вкладке браузера
interface BookDTO {
  // id: ...
  // title: ...
  // author: ...
  // ...допишите по наблюдению
}
```

### Шаг 5. Добавьте функции маппинга

**Зачем:** маппинг — это преобразование данных из одного формата в другой. Ваш `Book` и серверный `BookDTO` различаются: во внутренней модели `authors` — массив строк, а сервер отдаёт одно поле `author` со строкой. Функции-мапперы `mapFromServer` (DTO → Book) и `mapToServer` (Book → DTO) — это единственный место в коде, где два формата знают друг о друге. Отсюда три выгоды: (1) внутренняя модель остаётся чистой и не подстраивается под сервер; (2) если сервер завтра переименует поле, вы поправите одну функцию, а не всё приложение; (3) компилятор не даст забыть про преобразование — без маппера типы просто не сойдутся.

**Как:** добавьте обе функции. `mapToServer` готова, в `mapFromServer` заполните одно поле:

```typescript
// Маппинг: сервер -> приложение
function mapFromServer(dto: BookDTO): Book {
  // TODO 1: дополните преобразование.
  // Подсказка: Book.authors — массив строк, а сервер дал одну строку в dto.author
  return {
    id: dto.id,
    title: dto.title,
    authors: [], // ← замените на корректное преобразование
    year: dto.year,
    rating: dto.rating,
  };
}

// Маппинг: приложение -> сервер (готово, не менять)
function mapToServer(book: Book): BookDTO {
  return {
    id: book.id,
    title: book.title,
    author: book.authors[0] ?? '',
    year: book.year,
    rating: book.rating,
  };
}
```

### Шаг 6. Перепишите `fetchBooks` на настоящий GET-запрос

**Зачем и как устроено, по шагам:**
1. `fetch(API_URL)` отправляет GET-запрос и возвращает `Promise<Response>`. Важно: `Response` — это **не данные**, а «конверт» со статусом, заголовками и телом, которое ещё нужно прочитать.
2. Проверка `response.ok` обязательна, потому что `catch` **не ловит** ответы 404 и 500: для `fetch` ошибкой считается только сбой самой сети. Неположенный статус превращаем в ошибку сами (слайд 23 лекции).
3. `response.json()` читает тело ответа и тоже возвращает Promise: тело читается потоком, поэтому нужен `await`.
4. `dtos.map(mapFromServer)` превращает каждый серверный DTO во внутреннюю книгу — здесь вступает в силу маппинг из шага 5.

**Как:** полностью замените тело функции `fetchBooks` на:

```typescript
// Загрузка книг: настоящий GET-запрос к серверу
export async function fetchBooks(): Promise<Book[]> {
  // 1. Отправляем запрос и получаем «конверт» Response
  const response = await fetch(API_URL);

  // 2. Проверяем статус: 404 и 500 в catch не попадут,
  //    поэтому бросаем ошибку сами
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  // 3. Читаем тело ответа: json() асинхронный, нужен await
  const dtos: BookDTO[] = await response.json();

  // 4. Преобразуем каждый DTO во внутренний формат Book
  return dtos.map(mapFromServer);
}
```

### Шаг 7. Замените `saveBooks` на `saveBook`

**Зачем:** в имитации вы каждый раз перезаписывали весь массив в `localStorage` — поэтому функция принимала массив и ничего не возвращала. Настоящий REST-сервер работает с отдельными записями: `POST` на адрес `/books` создаёт **одну** запись, сам присваивает ей `id` и возвращает созданный объект в ответе. Поэтому новая функция принимает одну книгу, а возвращает одну книгу — ту, что подтвердил сервер, с серверным `id`.

**Как:** удалите функцию `saveBooks` и добавьте:

```typescript
// Создание книги: POST-запрос одной записи
export async function saveBook(book: Book): Promise<Book> {
  const response = await fetch(API_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(mapToServer(book)),
  });
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  // Сервер вернул созданный объект с присвоенным id
  const dto: BookDTO = await response.json();
  return mapFromServer(dto);
}
```

Обратите внимание на три детали: `method: 'POST'` обязателен (без него ушёл бы GET), заголовок `Content-Type` сообщает серверу, что тело — JSON, а в `body` уходит результат `mapToServer`, потому что сервер ждёт свой формат, а не ваш.

### Шаг 8. Добавьте `deleteBook`

**Зачем:** по той же логике REST удаление одной записи — это запрос `DELETE` на адрес конкретной записи: `/books/{id}`. Тело ответа у такого запроса пустое, читать через `json()` нечего, поэтому функция возвращает `Promise<void>`: важен сам факт успеха.

**Как:** добавьте функцию:

```typescript
// Удаление книги: DELETE-запрос по адресу записи
export async function deleteBook(id: string): Promise<void> {
  const response = await fetch(`${API_URL}/${id}`, {
    method: 'DELETE',
  });
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  // Тело ответа пустое — читать нечего
}
```

**Итог шага:** файл `src/api.ts` больше ничего не знает про `localStorage`, `delay` и случайные числа. Он умеет три вещи: читать список книг, создавать книгу и удалять книгу — настоящими HTTP-запросами.

**Понятия и механизм запроса**
1. Чем endpoint отличается от API? Приведите пример своего endpoint. Ответ: API — общий интерфейс с набором endpoints; endpoint — конкретный адрес, например `https://6afd8a922a9c141d36b8a7a2.mockapi.io/api/v1/book/4`.
2. Какой HTTP-метод использует браузер, когда вы просто открыли URL ресурса во вкладке? Ответ: обычно GET.
3. Чем `response.status` отличается от `response.ok`? Какие статусы попадают в `ok`? Ответ: `status` — числовой HTTP-код, а `ok` — признак успешного ответа (коды 200-299).
4. Почему `catch` не срабатывает при ответе 500 и зачем тогда нужна проверка `response.ok`? Ответ: HTTP 500 — не сетевая ошибка, а ответ, который говорит, что сервер сломан; проверка `response.ok` позволяет самим выбросить ошибку для неуспешного статуса.
5. Зачем нужен `await` перед `response.json()`? Что окажется в переменной без него? Ответ: `await` дожидается чтения JSON; без него в переменной будет Promise.
6. Проверяет ли приведение `as Book[]` данные во время выполнения программы? Ответ: нет, оно только подсказывает тип компилятору.
7. Что делает `JSON.stringify` и почему объект нельзя передать в `body` напрямую? Ответ: превращает объект в JSON-строку; поскольку `fetch` отправляет текст.
8. Зачем в POST-запросе заголовок `Content-Type: application/json`? Ответ: он сообщает серверу, что тело запроса содержит JSON.

**DTO и маппинг**
9. Что такое DTO и почему это отдельный интерфейс, а не сам `Book`? Ответ: DTO описывает формат данных сервера; отдельный тип отделяет его от внутренней модели приложения.
10. Сервер переименовал поле `author` в `writer`. Какие строки кода придётся изменить и почему только они? Ответ: поле в `BookDTO` и обращения к нему в функциях маппинга; остальные части приложения используют `Book`.
11. Что сломается и где именно, если в `mapFromServer` написать `authors: dto.author` без квадратных скобок? Ответ: выдаст ошибку: `string` нельзя присвоить `string[]`.
12. Почему `fetchBooks` возвращает `Book[]`, хотя внутри работает с `BookDTO[]`? Ответ: она преобразует каждый DTO в `Book` и возвращает уже внутренние модели.
